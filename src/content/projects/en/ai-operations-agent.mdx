## The problem

For a carpentry and roofing company, the inbox *is* the backlog. Signed quotes come
back as PDF attachments, complaints arrive mixed in with payment notices, and one
person re-types all of it into the CRM by hand.

Nothing gets lost, because somebody is always watching. That vigilance is the cost.

## The constraints

Three, and they shaped every decision that followed.

The mailbox is real and so is the CRM. A wrong write does not produce a bug report —
it produces an invoice sent twice and a client who notices.

The model must never invent. An extracted quote number that merely *looks* plausible
is worse than no number at all.

And it had to run unattended, on a schedule, without a human checking each decision.

## The system

An agent built on Claude with **15 tools**: searching sites and client records,
reading attached files, querying suppliers and unpaid invoices, flagging signals,
proposing a change. The agent decides which to call — it is not a fixed pipeline
with a model bolted on.

Around it: ingestion from Gmail and Microsoft Graph, classification by message type,
PDF extraction on quote attachments, and a reply left in draft for a human to send.

## The architecture

The decision that matters is what the agent is **not** allowed to do.

The client's live database is **read-only**. Writes default to `dry_run`. The single
exception is narrow and written down — a status field may move to "scheduled", nothing
else. Everything else the agent would change lands in a **proposal queue** that a
person approves.

That guard was not added late to reassure anyone. It is the reason the system can run
unattended at all.

The tool count went down over time, not up. 22 were dropped in one pass once I
measured they were writing with a token that cannot even see the real destination
pages — a tool that cannot succeed should not be offered to the model, even if it
makes the total look more impressive on paper.

## Reliability

**1065 tests, 1060 green.** They cover the tool layer, the extraction,
idempotence — the same mail processed twice must not create two records — webhook
authentication, and the security perimeter.

Sentry watches production. A few tests fail in a sandbox with no GitHub token: an
environment failure, recorded as such rather than quietly excluded from the count.

## Outcomes

In production since **May 2026**, version 4.2.0, deployed on Railway, 266 commits
between May and September.

The result worth stating is not a time saving I cannot measure. It is this: **no write
reaches the client's real data without a human approving it**, and the tool layer is
covered by a suite that runs in fifteen seconds.

## Limits

No usage instrumentation exists. I cannot tell you how many messages were processed,
and I will not estimate it.

The write path is deliberately manual, which caps how far the automation can go.

And there is one client. Everything here is proven against one real workload — not
against many.
