<Section
  surtitre="Production incidents"
  titre="Four failures, and what they changed."
  chapo="Each one left a written check that can be replayed."
>
  <Figure titre="01 · Lost draft">
    <Incident
      labels={etiquettes}
      titre="A technician lost a report they had already filled in"
      quand="July, back from a job site"
      hypothese="The draft was saved on every entry and every photo. Coming back to the app should find it."
      panne="They left the app during a report. On return they were on the home screen, and the draft's photos were gone."
      cause="Five defects chained together: a cache serving a stale version, photo storage that had become private, a race between two operations, expired image URLs and a fragile sync. The draft existed, but reopening it required a button they never saw, and the photo was still being written to the local database when they left the app."
      correctif="Reopening the app on an active draft reopens the report at the saved step. The draft waits for its photos to finish writing before it is saved, and it is also saved when the app is left."
      preuve="Invariant tests cover the chain by reading the shipped source. The live version is checked by downloading the deployed service worker."
    />
  </Figure>
  <Figure titre="02 · Invisible photos">
    <Incident
      labels={etiquettes}
      titre="Every photo disappeared, with no data lost"
      quand="July, reported as “no photos on a job”"
      hypothese="Photo storage is private: the app signs temporary URLs to display them, and keeps a public URL as a fallback."
      panne="Every photo disappeared at once, for every user, with no error message."
      cause="On private storage, a public URL returns an error: the fallback had never worked. All URLs were signed in one batched call whose failure was swallowed. A single transient network error emptied the whole display, while every file and every row was intact."
      correctif="Valid signed URLs are kept across reloads, the display rebuilds from them at startup, and signing runs in small isolated batches: a failed batch only blocks its own photos."
      preuve="A three-layer diagnosis, written and replayable: does the row exist, does the file exist, does signing work. Three yeses mean nothing is lost and the defect is in the display."
    />
  </Figure>
  <Figure titre="03 · Sync queue">
    <Incident
      labels={etiquettes}
      titre="An entry typed during a sync disappeared"
      quand="July, found by an adversarial audit"
      hypothese="Send pending records one by one, then rewrite what remains in the queue. The code had run that way for months."
      panne="Anything typed during a sync could be lost. The server had one version, the screen another, and no send was left to close the gap."
      cause="Read the queue, send, rewrite the queue: the network separates those three moments, and the rewrite erased entries added in between. The existing timestamp could not detect it, because it is deliberately kept on re-queue for conflict detection."
      correctif="Every entry carries a revision counter that changes on every edit. On acknowledgement the queue is re-read, and a send's result is only applied if the revision has not changed. Whatever was added during the send stays in the queue."
      preuve="The merge rule lives between two markers in the source, and a script tests exactly that zone: moving the code without moving the test makes the script fail."
    />
  </Figure>
  <Figure titre="04 · False success">
    <Incident
      labels={etiquettes}
      titre="A button said “done” and deleted nothing"
      quand="Found while writing a test against the real database"
      hypothese="The database isolates data per company, row by row. The rules were written and reviewed."
      panne="A reset button reported success every time and removed no rows, for weeks. Nothing failed, so nobody noticed."
      cause="When a delete matches no security policy, PostgreSQL returns no error: the query succeeds and deletes zero rows. From the app, a silent refusal looks exactly like success."
      correctif="Isolation is checked with a real technician account on the real database: the check creates a throwaway record and tests what that account can and cannot reach."
      preuve="The check runs with a technician's rights and fails if a rule is missing, the very case it was written for."
    />
  </Figure>
